# GRI Intelligence Platform — Project Brain

## What This Project Is

A full-stack system to:
1. **Store** all GRI standards as structured JSON (lightweight, code-friendly)
2. **Extract** ESG data from any company sustainability PDF automatically
3. **Query** via AI + RAG — natural language questions answered from actual report text

This is not a one-off script — it is a **platform**. Every piece of code written here should fit the architecture below.

## GRI Standards — JSON Schema

Every GRI standard JSON follows this shape:

```json
{
  "standard_id": "GRI 305",
  "name": "Emissions",
  "version": "2016",
  "effective_date": "2018-07-01",
  "category": "topic",
  "pillar": "environment",
  "sector_applicability": ["all"],
  "purpose": "...",
  "disclosures": [
    {
      "code": "305-1",
      "title": "Direct (Scope 1) GHG emissions",
      "type": "quantitative",
      "requirements": [],
      "guidance": "",
      "related_sdgs": ["SDG 13"]
    }
  ],
  "management_approach": {
    "code": "3-3",
    "applies": true
  }
}
```

Category values: `"universal"` | `"sector"` | `"topic"`
Pillar values: `"environment"` | `"social"` | `"governance"` | `"economic"`

## Company Report — JSON Schema

Output of `sustainability_extractor.py`. Stored in `output/` (and optionally `gri_repo/companies/`).

```json
{
  "metadata": {
    "company_name": "Sony Group Corporation",
    "report_year": "2025",
    "report_type": "Sustainability Report",
    "sector_standard": null,
    "total_pages": 208,
    "extraction_ts": "2026-07-21T10:00:00"
  },
  "gri_coverage": [
    {
      "sr_no": 1,
      "gri_topic": "Climate Change",
      "underlying_standard": "GRI 302: Energy 2016 + GRI 305: Emissions 2016",
      "coverage_rating": "Strong",
      "pages": "45, 46, 95, 112",
      "disclosures": "302-1, 302-2, 305-1, 305-2",
      "reported": true,
      "found_disclosures": ["302-1", "302-2", "305-1", "305-2"],
      "expected_disclosures": ["302-1", "302-2", "302-3", "305-1", "305-2", "305-3"],
      "coverage_pct": 66.7
    }
  ]
}
```

Key fields:
- `pages` — comma-separated exact page numbers where GRI codes were found
- `reported` — `true` if at least one expected disclosure code was found; `false` topics are filtered from Excel
- `sector_standard` — `"GRI 14"` for Vedanta (mining), `null` for Sony/Infosys/Wipro
- Sector-specific codes (e.g. `14.6.2`) show with labels: `"14.6.2 (tailings disposal methods)"`

## How the Extractor Works

`sustainability_extractor.py` runs in 5 steps:

1. **Load GRI corpus** — reads all `gri_repo/standards/*.json` files into memory keyed by `standard_id`
2. **Extract PDF text** — PyMuPDF primary (handles Asian-layout PDFs); pdfplumber fallback
3. **Extract hyperlinks** — PyMuPDF internal links; GRI content indices often hyperlink disclosure codes to actual data pages — destination page is used as the reporting page
4. **Match by code** — searches every page for GRI disclosure codes (e.g. `302-1`, `14.6.2`) via regex; no keyword matching
5. **Save** — `output/<Company>_<Year>.json` + `.xlsx` (single GRI Coverage sheet showing only reported topics)

### GRI_TOPICS structure (in sustainability_extractor.py)

```python
GRI_TOPICS = {
    "Climate Change": {
        "standard_ids": ["GRI 302", "GRI 305"],   # loads codes from JSON corpus at runtime
        "sector_disclosures": {},                  # no sector-specific codes for this topic
    },
    "Tailings": {
        "standard_ids": [],
        "sector_disclosures": {
            "GRI 14": {                            # only applied when company.sector_standard = "GRI 14"
                "14.6.2": "tailings disposal methods",
                "14.6.3": "tailings facilities",
            },
        },
    },
}
```

- `standard_ids` → GRI standard IDs; disclosure codes loaded from `gri_repo/standards/*.json` at runtime (not hardcoded)
- `sector_disclosures` → sector-specific codes keyed by sector standard ID; only applied when the company's `sector_standard` matches

### Sector standard logic

| Company | sector_standard | What codes are checked |
|---|---|---|
| Vedanta | `"GRI 14"` | All topic standard codes + GRI 14 sector-specific codes (14.6.2, 14.8.4, etc.) |
| Sony | `null` | Topic standard codes only; sector-specific topics (Tailings etc.) have no codes → not reported |
| Infosys/Wipro | `null` | Same as Sony |

### Coverage rating (code-based)

```
found_codes / expected_codes × 100:
  ≥ 75%  → Strong
  ≥ 50%  → Moderate
  > 0%   → Partial
  = 0%   → Minimal / Not reported (filtered from Excel)
```

## Tech Stack

```
Backend:    FastAPI (Python)
Frontend:   Next.js 14 + TypeScript + Tailwind CSS
LLM:        OpenRouter API (OpenAI-compatible) — free open models
            Default model: meta-llama/llama-3.1-8b-instruct:free
Embeddings: sentence-transformers (all-MiniLM-L6-v2) — local, free
Vector DB:  ChromaDB now (local, zero setup) → Qdrant later (production)
Chunking:   Python stdlib textwrap.wrap() — word-aware, no dependencies
PDF work:   PyMuPDF primary, pdfplumber fallback
Storage:    JSON files (standards + company reports)
```

### OpenRouter Setup (one-time)
```python
from openai import OpenAI

client = OpenAI(
    base_url="https://openrouter.ai/api/v1",
    api_key=os.environ["OPENROUTER_API_KEY"],
)
```
Free models: `meta-llama/llama-3.1-8b-instruct:free`, `google/gemma-2-9b-it:free`, `mistralai/mistral-7b-instruct:free`

### RAG Architecture

```
Ingest pipeline (run once per document):
  PDF → extract_text_by_page() → textwrap chunk (2000 chars, 200 overlap)
  → embed (sentence-transformers/all-MiniLM-L6-v2, runs locally)
  → upsert into ChromaDB collection per company

Query pipeline (per chat message):
  question → embed → similarity search top-8 chunks from ChromaDB
  → build context string → OpenRouter LLM with system prompt
  → return answer + source pages cited
```

Collection naming: `company_{slug}_{year}` e.g. `company_sony_2025`

## Conventions

- All JSON uses `snake_case` keys
- Coverage ratings: `"Strong"` | `"Moderate"` | `"Partial"` | `"Minimal"`
- GRI disclosure codes: format `"305-1"` (no "GRI" prefix in code fields)
- Company slugs: lowercase with underscores — `"sony_group_corporation"`, `"vedanta_limited"`
- Year field: string, not int — `"2025"`, `"FY2024"`
- Never hardcode company names in logic — always read from config/JSON
- `sustainability_extractor.py` is the single source of truth for extraction logic
- PyMuPDF is always the primary PDF extractor; pdfplumber is fallback only

## Key Design Decisions

- **Code-only matching** — extractor searches PDF text for GRI disclosure codes (e.g. `302-1`) only; no keyword heuristics; more precise, zero false positives from unrelated mentions
- **Hyperlink-aware pages** — internal PDF hyperlinks (e.g. GRI content index linking to data pages) are followed; destination page recorded as the reporting page, not the index page
- **Loads from JSON corpus** — expected disclosure codes come from `gri_repo/standards/*.json` at runtime; adding a new standard to the corpus automatically extends coverage
- **Sector standard per company** — `CONFIG["sector_standard"]` controls which sector-specific codes are added (e.g. `"GRI 14"` adds Tailings, Closure, Land Rights codes for Vedanta)
- **Filter unreported topics** — topics with 0 found codes are excluded from Excel output; JSON retains all topics for completeness
- **JSON over SQL** for the document store — no schema migrations, human-readable, works directly with RAG chunking
- **ChromaDB local first** — zero infra cost during development; swap to Qdrant for production with one config change
- **Extraction is always offline** — PDFs are processed once; website reads JSON, not PDFs at query time
